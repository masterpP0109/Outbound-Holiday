# Outbound Holidays backend

## Delivered architecture and local verification

The existing Vite/React frontend is retained. Express/TypeScript serves /api/v1 on Render; Prisma 6 uses PostgreSQL on Neon. Vercel hosts only the frontend. Neon project little-cherry-82979985 is linked to production, with Auth, five image buckets and the requested hello function deployed. The full Express API still requires a Render deployment and production hosting verification. See DOCKER_AND_IMAGES.md for Docker deployment and WebP upload commands.

Content is read from published database records, validated with Zod, and installed into a typed browser catalog. There is no runtime fixture fallback. A prerendered, previously published API snapshot can remain visible with an explicit refresh failure banner. Forms always need a successful live save. Content is refreshed on focus after its cache expires. The build fetches the configured API and fails if unavailable; it never imports fixture content. Rebuild the Vercel frontend after publishing changes so static HTML and the sitemap reflect them.

## Local setup

Run npm ci, configure ignored .env, then npm run dev:db for the optional local PostgreSQL at 127.0.0.1:55432. This Windows helper creates outbound_utf8 with UTF8 encoding. Set DATABASE_URL and DIRECT_URL to the local database. Run npm run db:migrate and npm run db:seed. Start npm run dev:api (PORT=3002), then npm run dev -- --port 3100 --strictPort. Set APP_URL/ALLOWED_ORIGINS to the frontend origin and VITE_API_BASE_URL and PRERENDER_API_BASE_URL to http://localhost:3002/api/v1. Existing unrelated applications using port 3000 are left running.

Run npm run typecheck, npm run lint, npm run test:backend, npm run build:api, npm run build, npm run check:seo and npm run check:contacts. npm run test:browser uses installed Windows Chrome and the isolated frontend on port 3100 with a local database. It creates test-only example.test submissions and cleans them up. Never point tests at production. The database test suite also refuses remote URLs without an explicit opt-in.

## Neon and Render deployment

1. Choose the intended Neon project and production branch. DATABASE_URL is its pooled TCP URL; DIRECT_URL is its direct URL. Both must use sslmode=require. Keep both solely in Render and trusted maintenance environments. The API rejects remote database URLs without required TLS. Use a separate preview database for preview testing.
2. Import render.yaml into Render, connect the repository, and configure those URLs, APP_URL, ALLOWED_ORIGINS (exact frontend origins), and API_PUBLIC_BASE_URL ending /api/v1. Use the Docker runtime with ./Dockerfile and context ., leaving Docker Command empty. Its startup script validates settings, applies migrations and inserts missing content before starting the API. On a paid plan, migrations/insert-only seed can move to a predeploy step. Health is /health; readiness /ready checks the database. The listener uses Render PORT on 0.0.0.0 and closes gracefully on SIGTERM/SIGINT.
3. On Vercel set VITE_API_BASE_URL and PRERENDER_API_BASE_URL to the real Render /api/v1 URL, and optionally VITE_TURNSTILE_SITE_KEY. Build npm run build, output dist. vercel.json provides clean route URLs and leaves missing URLs as the generated 404. No database, SMTP, provider, cron or Turnstile server secret belongs in any VITE variable.
4. Deploy API/database first, verify /ready and /api/v1/content, then deploy Vercel and repeat browser/SEO checks against actual hosting. Exact production host configuration and live verification remain outstanding.

Render Free can sleep after inactivity. The client allows 75 seconds for genuine user requests; prerender allows 120 seconds, preserves inputs on errors, and offers retry. There is no fake keepalive. See https://render.com/docs/free. Select an always-on plan only after cost approval if response latency is important.

## API

Public GET /api/v1/content returns the validated coherent snapshot. /site, /homepage, /categories, /accommodation, /experiences, /packages, /guides and /gallery provide public sections. Catalog list routes accept q, category, tag, featured, minPrice, maxPrice, sort (recommended/price-asc/price-desc/name), page and limit. Invalid queries are 422; unknown slugs or unpublished records are 404. Singular detail URLs append the stable slug. Public reads exclude private enquiry/subscriber/outbox records.

POST /enquiries and /newsletter require JSON, approved Origin, UUID Idempotency-Key, honeypot/timing checks and optional Turnstile verification. Enquiries return saved=true and a durable OH reference only after a transaction stores both the enquiry and outbox jobs. Same-key conflicts are 409. Identical enquiries within ten minutes deduplicate across concurrent requests. Contact and trip fields have server limits; selected published IDs and estimates are verified from the database. The displayed itinerary draft, preferred email contact and client estimate are also retained, explicitly marked unverified; authoritative estimate data is stored separately. Enquiries have a private lifecycle status and updated timestamp. Prices are estimates and availability is not confirmed. Marketing consent is optional and separate from enquiries, required for newsletter requests.

The server caps JSON at 32 KB, validates all input, rate-limits through PostgreSQL, escapes email HTML, restricts CORS, and protects worker/provider endpoints with constant-time bearer authentication. There is no public admin/content write or private submission list endpoint. Turnstile is opt-in but should be configured for a public deployment. Local IP limits trust one proxy hop on Render; verify this setting for any different reverse proxy.

## Namecheap email and newsletter boundary

Delivery defaults to disabled. The exact purchased Namecheap product (Private Email versus cPanel/other), approved sender, mailbox SMTP settings and designated test recipient have not been supplied. Do not assume shared-hosting SMTP settings or bulk-mail permission apply to this mailbox. Confirm product-specific limits and terms: https://www.namecheap.com/support/knowledgebase/article.aspx/133/22/do-you-have-any-restrictions-on-sending-out-emails/ . The current Private Email limits page (updated 30 September 2026) lists Launch/Expand/Scale paid mailboxes at 500 emails/hour/mailbox and 50 recipients/message: https://www.namecheap.com/support/knowledgebase/article.aspx/10719/2179/email-sending-and-usage-limits-for-private-email/ . These limits do not establish that this particular purchased product permits bulk campaigns; confirm the exact plan and applicable terms first. No paid bulk-mail provider or subscription is required by this implementation.

EMAIL_PROVIDER supports disabled, smtp, or optional resend. For confirmed mailbox SMTP, configure SMTP_HOST, SMTP_PORT (465 implicit TLS or 587 required STARTTLS), SMTP_USER, SMTP_PASSWORD, EMAIL_FROM, TEAM_ENQUIRY_TO, EMAIL_MESSAGE_ID_DOMAIN. TLS certificates are verified. First use EMAIL_DELIVERY_MODE=test and EMAIL_TEST_TO so all email goes to the designated recipient. After verifying sender authentication, replies and mailbox acceptance, live sends to actual recipients. Never paste credentials into source or browser variables. SMTP acceptance is recorded as sent; it is not proof of inbox delivery. A crash after SMTP acceptance can cause a duplicate retry; the stable Message-ID aids correlation but SMTP offers no transactional idempotency guarantee. Optional Resend uses the durable job deduplication key and can poll reported delivery failures.

NEWSLETTER_PROVIDER=disabled durably stores pending consent and a confirmation job, and the UI explicitly says delivery awaits configuration. NEWSLETTER_PROVIDER=self-hosted uses the configured email adapter to deliver confirmation/unsubscribe links. Only POST /newsletter/confirm?token=... confirms consent; GET displays a confirmation page so email scanners cannot subscribe someone. Only POST /newsletter/unsubscribe changes the stored preference; GET asks for confirmation. Unsubscribe is durable immediately and stale confirmation jobs are cancelled. No campaign sending UI or scheduled bulk campaign system is introduced. If mailbox policy permits low-volume double opt-in confirmations, this requires no paid provider. If bulk sending is needed later, confirm provider and account before enabling the optional Brevo adapter. Brevo secrets/list/template/webhook are optional, not assumed. The signed bearer webhook verifies provider contact state before updating consent.

## Durable worker and retries

Enquiry save commits team notification plus customer acknowledgement jobs atomically. Notification stores attempt count, next attempt, lease, provider result, failure and final dead status. Workers claim with PostgreSQL SKIP LOCKED and leases, await delivery, and retry with bounded backoff up to eight attempts. A provider failure never rolls back a saved enquiry. Operators can inspect Notification with Prisma Studio in a trusted environment; correct configuration then explicitly requeue failed/dead records after checking whether mail was already accepted. Do not reset delivered mail indiscriminately.

npm run outbox:production runs the compiled independent worker with server-only credentials. Schedule it in a service that can run when the Render web service sleeps, or configure a paid Render cron job after cost approval (https://render.com/docs/cronjobs). No paid cron was created. The protected /api/v1/cron/outbox route can be invoked manually with CRON_SECRET for review/test, but repeatedly waking a free web service is not the recommended scheduler. Without an independent scheduler, notification and confirmation jobs remain queued until a manual worker run; continuous automatic delivery is not active. Subscriber preferences and enquiries are still persisted.

## Content maintenance and publishing

prisma/fixtures preserves the original migration source, including all 11 full guides, deeply nested property/experience/package payloads, editorial sections, builder choices and package-specific recommendation variants. npm run db:seed inserts missing records only and preserves edited records. Import is atomic and serializes concurrent import runs. --update is an explicit destructive replacement of fixture-managed content: use only after reviewing a backup/diff, never in routine deploy starts. npm run db:reconcile reports original-versus-database differences; edited payloads are expected to differ. docs/import-reconciliation.json records counts and unresolved relationships.

npm run content:export -- .local/content-export.json exports content, media and relations only (including drafts); it does not export personal submissions. For a single edit prepare JSON with id, expectedUpdatedAt (from export), title, optional metaTitle/metaDescription, status (draft/published/archived), complete payload, images (id/url/alt/caption/displayOrder/role), and relations (toId/type/displayOrder). Run npm run content:apply -- .local/change.json. It validates content shapes, stable identity, all foreign keys and optimistic timestamp, synchronizes starting price, and atomically replaces only that record's media/links. A concurrent edit rejects instead of overwriting. Preserve all complete nested content when editing. Maintain corresponding payload image URLs and Media records together. Use published status only after review; check APIs then rebuild the frontend. Contact details/currency/featured selections are in site:shared; home and shared editorial content is in its payload, with links supplying published featured entities. Section page metadata is in site.routeSeo; catalog records have editable metaTitle and metaDescription. Package hotel variants are separate packageStay records, preserving original descriptions even when not a directory property.

For private enquiry operations and status review use authenticated database access/Prisma Studio with least-privilege production credentials; no unauthenticated admin UI was added. Establish backup/restore, retention and access policies with the business before production operation. Secrets and local database files are ignored by git.

## Known verification limits

Local migrations, seeded data, API and prerender checks are independent of hosting access. Production deployment, Namecheap authentication/live delivery, inbox/bounce verification and automatic production scheduling are unverified. The current frontend production bundle is approximately 820 KB before gzip; the build warns about chunk size. npm audit reports a high-severity recursive-object merge advisory in the Prisma CLI dependency deepmerge-ts; this CLI processes trusted configuration, not public submissions. Resolve through a compatible maintained Prisma upgrade after migration review; do not force npm's suggested major/downgrade blindly. This does not represent a verified exploit in the public API.
